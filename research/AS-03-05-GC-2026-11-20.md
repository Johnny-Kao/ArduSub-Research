## AS-03 — SURFTRAK missing depth-sensor failure transition: VERIFIED

Real SITL: Dive while armed in ALT_HOLD, enter mode 21 (SURFTRAK), set `SIM_BARO_DISABLE=1`. The firmware reports `Depth sensor error!`.

**RED (untouched production source):** mode stays `custom_mode=21` (SURFTRAK), `armed=True` after failure. The source guard only falls back to MANUAL for ALT_HOLD, SURFACE and requires_GPS() modes. SURFTRAK inherits `requires_altitude()=true` but `requires_GPS()=false` and is excluded by that guard.

**GREEN (one-condition Research fix):** add `control_mode == Mode::Number::SURFTRAK` to the guard. Same fault injection produces `custom_mode=19` (MANUAL), `armed=True`; automatic mode fallback occurs. Clean green GC [#44677919864](https://github.com/Johnny-Kao/ArduSub-Research/actions/runs/44677919864) PASS with explicit disarm cleanup.

Scope of proof: faulty mode transition is confirmed; harmful thruster output / physical injury / damage NOT independently proven. Candidate is for serious maintainer review **after** evaluating impact and regression risk, not a confirmed uncontrolled acceleration defect.

## AS-04 — GUIDED terrain recovery: REAL RED / AUTO POSITIVE CONTROL GREEN

The original attempt only changed `RNGFND1_MAX`, which did not invalidate a scripted Lua rangefinder that continued reporting Good. This was a **test injection error**, and those earlier results are superseded.

The research-only Lua sensor now explicitly reports `OutOfRangeHigh` via `SCR_USER3=-101`. Actual ArduSub SITL then logs `Failsafe terrain triggered` and `Attempting auto failsafe recovery` in GUIDED, but remains armed in GUIDED beyond the 10-second recovery deadline, without `Terrain failsafe recovery timeout!`: [GUIDED RED #44682590280](https://github.com/Johnny-Kao/ArduSub-Research/actions/runs/44682590280).

Using the identical fault in AUTO with the pre-existing synthetic terrain mission executes the recovery timeout and default DISARM action: [AUTO positive control GREEN #44683779429](https://github.com/Johnny-Kao/ArduSub-Research/actions/runs/44683779429).

Source cause: `failsafe_terrain_on_event()` calls `mode_auto.auto_terrain_recover_start()` in both AUTO and GUIDED. Only AUTO dispatches `auto_terrain_recover_run()`; therefore GUIDED never executes its timeout and fallback action. Issue draft: [AS-04](./AS-04-issue-draft.md).

Scope: safety-state machine and absent configured fallback verified in complete SITL; harmful physical motion not demonstrated.

Additional AS-03 positive control: ALT_HOLD correctly switched to MANUAL under the same `SIM_BARO_DISABLE=1` failure, while SURFTRAK still stayed in mode 21: [comparison GC #44682590280](https://github.com/Johnny-Kao/ArduSub-Research/actions/runs/44682590280). Maintainer-facing [AS-03 draft](./AS-03-issue-draft.md).

## AS-05 — acceleration-only timeout: ACTUAL TELEMETRY COLLECTED, SAFETY IMPACT UNPROVEN

In armed GUIDED at depth approximately 10 m, submit `SET_POSITION_TARGET_LOCAL_NED` with zero target velocity and nonzero x acceleration of 1.5 m/s²; stop sending. Firmware source still has a guard that zeros acceleration only when velocity target is nonzero, so its target can remain stale. Observed after nominal 5 seconds: position approximately (6.33,-0.03,10.39) m and velocity x approximately 0.63 m/s, active servo PWM; after 8 seconds: position approximately (6.88,0,10.38) m, velocity x approximately 0.02 m/s, active PWM. This is **not proof of sustained runaway**. The test does not compare a zero-acceleration baseline nor establish an unacceptable actual commanded thrust. No SmartPR promotion based on these results.
